# 홈페이지 예약·결제 통합 계획

작성일: 2026-08-27
대상: `sht-homepage`에 `sht-platform`의 고객 예약·결제 기능을 신규 구현

## 결론

기존 플랫폼은 코드·DB 계약·운영 흐름을 변경하지 않고 그대로 유지한다.
홈페이지에는 고객용 예약·결제 화면을 별도로 구현하며, 완성·검증·승인 전까지
기존 고객 플랫폼과 병렬 운영한다. 매니저는 계속 기존 플랫폼에서 예약을
처리한다.

회원·예약·견적·결제 원장은 기존 플랫폼 Supabase 한 곳에만 둔다. 홈페이지
Supabase는 플랫폼 상품을 가공한 공개 캐시, 홈페이지 전용 콘텐츠, 그리고 고객이
선택한 **장바구니 초안**만 유지한다. 장바구니는 예약이나 결제가 아니며, 고객이
예약 확정을 요청하기 전에는 플랫폼 DB에 어떤 예약 행도 만들지 않는다.

```text
플랫폼 상품 원본 ──읽기/동기화──> 홈페이지 고객 화면
        │                         │
        │                         ├─ 플랫폼 인증으로 로그인
        │                         ├─ 홈페이지 DB에 장바구니 초안 저장
        │                         ├─ 예약 확정 후에만 기존 데이터 계약으로 예약 생성
        │                         └─ 결제 상태·확정서 표시
        ▼
플랫폼 매니저 화면 ── 예약 처리·OnePay 링크 발급·확정

기존 고객 플랫폼 ───────────────────────── 병렬 운영 유지
```

## 점검 결과

- 홈페이지와 예약 플랫폼은 서로 다른 Supabase 프로젝트다.
- 회원 인증은 홈페이지에서도 예약 플랫폼 프로젝트를 사용하고 있다.
- 기존 플랫폼 저장소는 홈페이지 저장소 밖에 있으며, 이번 작업에서 읽기 점검만
  하고 어떠한 파일도 변경하지 않는다.
- 플랫폼 상품 원본은 홈페이지 `*_v2` 공개 캐시로 동기화되고 있으며, 활성
  크루즈 25개·객실 219개·요금 854개가 확인됐다.
- 활성 요금 854개 모두 플랫폼 원본 `cruise_rate_card.id`를
  `rate_plans_v2.source_rate_id`로 보존하고 있어 두 DB를 안전하게 연결할 수
  있다.
- 기존 상품 상세의 예약 폼은 홈페이지 구형 `reservations`에 직접 INSERT한다.
  그러나 이 테이블은 빈 구형 `cruises/cabins`에 외래키가 걸려 있고 INSERT
  RLS 정책도 없어 현재 v2 상품으로는 정상 접수될 수 없다.
- 플랫폼 고객 앱은 인증된 고객이 기존 RLS 아래에서 `reservation`과 서비스별
  상세 테이블을 직접 작성한다. 홈페이지도 이 기존 계약을 그대로 사용한다.
- OnePay create/return/notify 코드는 플랫폼에 있으나 create 권한이
  manager/admin으로 제한되어 있고, 현재 고객 흐름은 매니저가 발급한 가상결제
  링크를 전달하는 방식이다. 이 보안 경계는 변경하지 않는다.

## 목표 흐름

1. 고객이 홈페이지에서 서비스와 상품을 선택한다.
2. 비로그인 고객은 플랫폼 계정으로 로그인한 뒤 같은 홈페이지 URL로 복귀한다.
3. 홈페이지가 플랫폼 원본 ID로 활성 상태·적용 기간·가격을 다시 조회한다.
4. 고객이 장바구니 저장을 요청하면 일반 서비스는 새 견적을 자동 생성해 묶고,
   패키지는 기존 고객앱 계약대로 별도 예약으로 저장한다. 고객이 기존 견적을
   선택하는 단계는 제공하지 않는다.
5. 매니저가 기존 플랫폼에서 예약 가능 여부와 금액을 검토·처리한다.
6. 매니저가 기존 방식으로 OnePay 결제 링크를 발급하고 고객에게 전달한다.
7. 홈페이지는 고객 소유 예약과 결제 상태를 플랫폼 원장에서 조회해 보여준다.
8. 홈페이지 자체 결제 링크 발급은 별도 보안 검증을 모두 통과한 뒤에만 연다.

## 구현 단계

### 0. 안전 경계와 병렬 운영 — 완료

- [x] 구형 홈페이지 `reservations` INSERT 제거
- [x] 플랫폼 원본 요금 ID를 공개 v2 조회 모델에 추가
- [x] 저장소 지침에 플랫폼 무수정·병렬 운영 원칙 추가
- [x] 홈페이지 신규 예약을 베타로 표시하고 기존 플랫폼 진입점 유지
- [ ] 서비스별 회귀 테스트와 운영 승인 전환 체크리스트 작성

### 1. 홈페이지 고객 예약 기반

- [x] 홈페이지 내부 `/booking`에 8개 서비스 진입점을 만든다.
- [x] 로그인 리다이렉트 전 홈페이지 URL 전체를 안전한 `next` 값으로 보존한다.
- [x] `/booking/reservations`에서 고객 본인의 예약·결제 상태를 조회한다.
- [x] 크루즈에서 플랫폼 원본 요금 ID의 활성 상태와 적용일을 재검증하고 로컬
  예약 초안을 저장한다. 이 단계에서는 플랫폼 예약 원장을 쓰지 않는다.
- 아동·유아 규정, 객실 배치, 프로모션, 할증까지 기존 계산기와 결과가 일치한
  뒤에만 실제 예약 쓰기를 활성화한다.

완료 기준: 홈페이지 안에서 로그인·선택·예약 생성·내역 확인이 이어지고,
동일 입력에 대한 플랫폼 고객 앱과 홈페이지의 금액·저장 행이 일치한다.

### 2. 전 서비스 이전

- [x] 크루즈·호텔 상품 선택을 홈페이지 공용 장바구니에 연결한다.
- [x] 8개 서비스 타입을 수용하는 공용 장바구니 계약과 통합 체크아웃 화면을
  만든다.
- [x] 로그인 고객의 장바구니를 홈페이지 DB `homepage_booking_carts`에
  사용자별로 저장하고, 다른 기기에서도 조회한다. 플랫폼 DB에는 이 단계에서
  예약·결제·견적 행을 만들지 않는다.
- 크루즈, 크루즈 차량, 공항 이동, 호텔, 렌터카, 투어, 패키지, 티켓을 순서대로
  이전한다.
- 각 서비스는 기존 플랫폼의 서비스별 상세 테이블과 상태값을 그대로 사용한다.
- 서비스별 최소 1건의 생성·수정·취소·매니저 처리 회귀 테스트를 통과한다.
- 기존 고객 플랫폼은 이 단계 전체에서 계속 운영한다.

### 3. 견적·고객 결제

- 고객 본인 예약만 결제할 수 있는 서버 API를 만든다.
- 결제 가능 상태, 미결제 잔액, 통화, 금액을 서버에서 재검증한다.
- OnePay 요청 참조값과 IPN 이벤트에 고유 제약을 두어 중복 처리를 막는다.
- 결제 상태 갱신, 견적 상태 갱신, 감사 로그를 DB 함수/트랜잭션으로 묶는다.
- 실패·취소·타임아웃·중복 IPN을 테스트한다.

완료 기준: 테스트 결제 1건이 중복 반영 없이 `completed`가 되고, 다른 사용자의
결제 ID로 요청하면 403이 반환된다.

1차 운영에서는 기존처럼 매니저가 발급한 OnePay 링크로 고객이 결제하고,
홈페이지는 결제 상태를 표시한다. 홈페이지에서 결제 링크 자체를 만들려면 아래
항목을 별도 승인·구현한다.

현재 플랫폼의 OnePay create API는 manager/admin 전용이고 결제 URL은 DB에
보존되지 않는다. 따라서 홈페이지 체크아웃은 고객 소유 예약의 결제 대기
레코드와 합계까지 표시하되, 고객용 링크 발급 API의 소유권 검증·통합 결제
멱등 처리·서명 콜백이 완료되기 전에는 결제 버튼을 활성화하지 않는다.

### 4. 예약 후속 처리

- 결제 완료 화면, 예약 목록, 영수증과 확정서를 연결한다.
- 예약 변경·취소 및 환불 상태를 동일 원장에서 관리한다.
- 운영자 알림과 고객 알림은 결제 트랜잭션과 분리된 재시도 가능한 작업으로
  보낸다.

### 5. 전환

- 390px·1440px UI, 서비스별 저장 결과, 플랫폼 매니저 처리, 결제 상태 반영,
  실패 복구를 검수한다.
- 병렬 운영 지표와 고객 문의를 확인한 뒤 사용자 승인으로만 홈페이지를 기본
  고객 진입점으로 전환한다.
- 기존 고객 플랫폼 종료 또는 리다이렉트는 별도 작업으로 수행한다.

## DB 원칙

- 홈페이지 DB에는 예약·결제 원장을 새로 만들지 않는다.
- 홈페이지 DB의 `homepage_booking_carts`는 플랫폼 인증 UUID로 식별하는
  선택 초안 전용 테이블이다. 플랫폼 JWT는 홈페이지 RLS를 통과할 수 없으므로,
  홈페이지 서버가 플랫폼 토큰을 검증한 뒤 service role로 해당 UUID 행만
  읽고 쓴다. 브라우저에는 홈페이지 service-role 키를 절대 노출하지 않는다.
- 장바구니의 표시 가격은 참고값이다. 예약 확정 요청 때 플랫폼이 재고·가격·
  상품 상태를 재검증한 뒤에만 플랫폼 예약/견적/결제 원장을 만든다.
- 홈페이지 공개 뷰에는 연결에 필요한 플랫폼 원본 ID만 노출한다.
- 플랫폼 DB의 테이블·컬럼·RLS·함수·트리거는 별도 승인 없이 변경하지 않는다.
- 필요한 컬럼이 생기면 먼저 기존 JSON/메타데이터 계약으로 해결 가능한지
  검토하고, 불가능할 때 영향 분석·롤백·병렬 호환 계획을 승인받은 뒤 추가한다.
- 플랫폼 INSERT/UPDATE는 인증 사용자 소유권을 확인하는 RLS 또는 서버
  API/RPC를 거친다.
- 가격은 브라우저·URL·홈페이지 캐시 값을 신뢰하지 않는다.
- 결제 완료는 서명 검증된 서버 알림을 기준으로 하고 멱등 키를 강제한다.
- service role/secret key는 서버 전용이며 `NEXT_PUBLIC_` 변수에 두지 않는다.

## 별도 보안 조치

홈페이지 프로젝트에서 아래 구형 9개 관계의 RLS가 꺼져 있다는 Advisor 경고가
확인됐다: `cruise_holiday_surcharge`, `cruise_info`, `cruise_info_view`,
`cruise_location`, `cruise_promotion_rate`, `cruise_promotion`,
`cruise_rate_card`, `cruise_rooms_view`, `cruise_tour_options`.

즉시 RLS만 켜면 기존 조회가 중단될 수 있으므로 이번 예약 변경에는 포함하지
않는다. 실제 사용처와 필요한 공개 컬럼을 확인한 뒤 읽기 전용 뷰 또는 명시적
SELECT 정책으로 전환하고, anon/authenticated의 쓰기 권한을 제거하는 별도
마이그레이션으로 처리한다.
