# 크루즈 추천 운영순위 관리 계획

작성일: 2026-09-05

## 1. 결론

추천순위는 현재의 `추천 점수`에 숫자를 더하는 방식보다, **적합성 검증을 통과한 크루즈를 대상으로 관리자가 지정한 운영순위를 먼저 적용하는 방식**이 적절하다.

운영순위는 크루즈 한 개의 고정 속성이 아니다. `추천 기준`과 `일정`이 같은 후보들 사이의 상대적 순서이므로, 크루즈별 상세 폼에 숫자 입력칸을 각각 두기보다 관리자 화면에 **추천 기준별 순위표**를 별도로 두고 전체 목록을 한 번에 재정렬·저장하는 방식을 권장한다.

핵심 원칙은 다음과 같다.

1. 일정, 출발일, 인원, 객실 정원과 객실 구성은 기존처럼 필수 적합성 조건으로 먼저 검증한다.
2. 필수 조건에 맞지 않는 크루즈는 운영순위가 1위여도 노출하지 않는다.
3. 필수 조건을 통과한 후보 중 현재 고객의 1순위 추천 기준과 일정에 맞는 운영순위를 적용한다.
4. 순위가 등록되지 않은 후보는 기존 추천 점수와 가격 순서로 이어서 정렬한다.
5. 운영순위는 홈페이지 전용 편집 데이터로 저장하고, 플랫폼의 예약·견적·결제 데이터 계약은 변경하지 않는다.

## 2. 현재 상태

### 고객 화면

`/travel-guide`는 현재 다음 순서로 추천을 계산한다.

- 일정과 출발일에 맞는 공개 요금만 조회
- 인원과 객실 구성에 맞지 않는 객실 제외
- 크루즈마다 가장 낮은 등록 성인 요금의 적합 객실 선택
- 기본 적합성, 추천 객실, 활성 추천 태그, 예산 적합성을 점수화
- 점수 내림차순, 동점이면 가격 오름차순으로 상위 3개 노출

고객은 추천 기준을 최대 2개까지 선택할 수 있고 선택한 순서는 상태에 보존되지만, 현재 결과 정렬에서는 두 기준의 우선도를 구분하지 않는다.

### 관리자 화면

`/admin`의 크루즈 `추천 기준`에서는 현재 크루즈별로 다음 항목만 관리한다.

- 추천 태그
- 고객에게 표시할 추천 근거
- 추천 사용 여부

여러 크루즈의 상대적 순서를 한 화면에서 비교하거나 같은 추천 기준 안에서 1위, 2위, 3위를 지정하는 데이터와 UI는 없다.

라이브 관리자 화면 점검 시 크루즈 데이터가 `0개`로 보이고 `데이터를 불러오는 중…` 상태가 유지되었다. 순위 기능 검수 전에 배포 환경의 `/api/admin/data` 응답과 관리자 데이터 로딩 상태를 먼저 확인해야 한다.

## 3. 추천 범위 정의

첫 버전의 순위 범위는 아래 두 값의 조합으로 제한한다.

| 범위 | 값 | 설명 |
| --- | --- | --- |
| 추천 기준 | `default` 또는 활성 추천 태그 | 고객이 추천 기준을 선택하지 않은 기본 순서와 태그별 순서 |
| 일정 | `ALL`, `DAY`, `1N2D`, `2N3D` | 전체 공통 순위 또는 일정별 순위 |

날짜, 인원, 객실 수, 객실 구성, 예산까지 모든 조합에 별도 순위표를 만들면 조합 수가 너무 많아지고 운영자가 어떤 표를 고쳐야 하는지 알기 어려워진다. 이 값들은 순위표 범위가 아니라 기존 적합성 필터와 점수 계산에 남겨 둔다.

조회 우선순위는 `추천 기준 + 해당 일정` → `추천 기준 + ALL` → `default + 해당 일정` → `default + ALL` 순서로 한다. 어느 범위에도 운영순위가 없으면 현재 추천 점수 정렬만 사용한다.

## 4. 고객이 추천 기준을 두 개 선택한 경우

현재 선택 순서가 보존되므로 첫 번째로 선택한 값을 `1순위 추천 기준`, 두 번째 값을 `보조 추천 기준`으로 명시하는 방식을 권장한다.

- 운영순위 조회: 1순위 추천 기준 사용
- 기존 추천 점수: 두 추천 기준을 모두 반영
- 고객 화면: 선택 상태에 `1순위`, `2순위` 표기를 추가해 숨은 규칙이 되지 않게 함
- 추천 결과 이유: 운영순위 자체나 내부 숫자는 고객에게 노출하지 않고, 기존 추천 근거만 표시

두 태그의 순위를 평균내거나 태그 조합별 순위표를 만드는 방식은 초기 운영에서는 피한다. 평균 순위는 운영자가 결과를 예측하기 어렵고, 태그 조합별 순위표는 관리 대상이 빠르게 증가한다.

## 5. 데이터 설계

홈페이지 Supabase에 `cruise_recommendation_priorities_v2` 테이블을 추가한다.

| 열 | 형식 | 규칙 |
| --- | --- | --- |
| `criterion_tag` | `text` | `default` 또는 태그 형식 검증을 통과한 값 |
| `schedule_type` | `text` | `ALL`, `DAY`, `1N2D`, `2N3D` 중 하나 |
| `cruise_id` | `uuid` | `cruises_v2(id)` 참조 |
| `position` | `smallint` | 1 이상, 범위 안에서 중복 금지 |
| `updated_by` | `uuid` | 마지막 저장 관리자 ID |
| `updated_at` | `timestamptz` | 마지막 저장 시각 |

권장 제약은 다음과 같다.

- 기본 키: `(criterion_tag, schedule_type, cruise_id)`
- 고유 키: `(criterion_tag, schedule_type, position)`
- 순위는 1부터 빈 번호 없이 서버에서 다시 매김
- 크루즈가 비공개이거나 추천 태그가 비활성화되면 순위 행을 바로 삭제하지 않고 관리자 목록에서 `적용 제외` 상태로 표시
- 공개 추천 API는 순위 테이블을 직접 노출하지 않음

순위 저장은 여러 행을 개별 PATCH하지 않고, 선택한 범위의 정렬된 `cruise_id[]` 전체를 한 번에 받는 서버 함수 또는 트랜잭션으로 처리한다. 기존 위치를 임시 범위로 이동한 뒤 새 위치를 1부터 다시 지정하면 교환 과정의 고유 키 충돌을 피할 수 있다.

운영 추적이 필요하므로 최소한 `updated_by`, `updated_at`을 남긴다. 복원과 책임 추적이 중요하면 별도 감사 테이블에 범위, 변경 전 순서, 변경 후 순서, 작업자, 저장 시각을 함께 기록한다.

## 6. 권한과 데이터 경계

- 조회와 저장 API는 기존 `getHomepageOperator` 인증을 사용한다.
- 순위 변경은 `admin` 역할만 허용하고 `manager`는 조회만 허용하는 것을 기본안으로 한다.
- 추천 엔진은 서버에서 홈페이지 서비스 역할 클라이언트로 순위를 조회한다.
- 브라우저의 익명 사용자에게 순위 테이블 SELECT 권한을 주지 않는다.
- 이 기능을 기존 `PLATFORM_PRODUCT_ACTIONS`에 넣거나 플랫폼 쓰기 API로 전달하지 않는다.
- 플랫폼의 크루즈, 예약, 견적, 결제 테이블·함수·엔드포인트는 변경하지 않는다.

## 7. 관리자 UI

현재 크루즈별 `추천 기준` 화면은 태그와 근거 관리 용도로 유지하고, 같은 메뉴 안에 `추천순위 편집` 구역을 추가한다.

### 상단 범위 선택

- 추천 기준 선택: 기본 추천, 가족, 커플, 발코니, 조용한 휴식, 액티비티, 가격, 럭셔리, 활성 사용자 태그
- 일정 선택: 전체, 당일, 1박 2일, 2박 3일
- 현재 적용 범위와 마지막 저장자·저장 시각 표시

### 순위 목록

- 한 행에 순위, 크루즈명, 활성 상태, 해당 태그 상태, 일정 제공 여부, 이동 버튼을 표시
- 마우스 드래그와 함께 `위로`, `아래로`, `맨 위로` 버튼을 제공해 키보드와 모바일에서도 조작 가능하게 함
- 조건에 사용할 수 없는 크루즈는 순위 목록에서 분리하고 제외 이유를 표시
- 순위가 없는 활성 크루즈는 `미지정` 목록에 두고 원하는 위치에 추가
- 숫자 직접 입력은 보조 기능으로만 제공하고, 입력 후 전체 순위를 자동 정규화

### 저장 방식

- 재정렬은 브라우저 상태에서만 반영하고 `순위 저장`을 눌렀을 때 한 번에 저장
- 저장 전 변경 행 수와 적용 범위를 요약
- 저장 성공 후 서버에서 다시 읽은 최종 순서를 표시
- 저장 실패 시 화면 순서를 유지하고 오류를 표시해 재시도 가능하게 함
- 다른 관리자가 먼저 저장한 경우 마지막 조회 버전과 비교해 덮어쓰지 않고 새로고침 안내

### 시각 원칙

Stay Halong 관리자 디자인에 맞춰 번호가 강조된 가로 행, 얇은 구분선, 각진 컨트롤을 사용한다. 선택 범위와 저장 버튼에만 acid yellow를 사용하고 둥근 카드, 그림자, 장식용 그라데이션은 사용하지 않는다. 모든 조작 버튼은 44px 이상의 터치 영역과 명확한 포커스 상태를 제공한다.

## 8. 추천 엔진 정렬 규칙

기존 필터와 후보 점수 계산 후 아래 순서로 정렬한다.

1. 일정·날짜·정원·객실 구성·활성 요금 필수 조건 통과
2. 현재 범위의 운영순위가 있는 후보 우선
3. 운영순위 `position` 오름차순
4. 같은 운영 상태에서는 기존 추천 점수 내림차순
5. 동점이면 등록 요금 오름차순
6. 마지막 안정 정렬은 크루즈 ID 또는 한글 이름 오름차순

이 규칙은 관리자가 지정한 1위가 **적합한 후보인 경우에만** 먼저 나오도록 보장한다. 운영순위 1위의 객실이 인원 조건을 충족하지 못하거나 해당 날짜에 활성 요금이 없으면 그 상품은 제외되고 다음 순위의 적합 상품이 올라온다.

반환 결과에는 내부 운영순위 값을 넣지 않는다. 필요하면 서버 로그에 적용한 범위와 순위 버전만 기록해 결과 재현에 사용한다.

## 9. API 변경안

### 관리자 조회

기존 `/api/admin/data` 응답에 다음을 추가한다.

- `recommendationPriorities`
- `recommendationPriorityRevision` 또는 범위별 마지막 수정 시각

대시보드 전체 로딩을 무겁게 만들지 않으려면 순위 편집 구역을 열 때만 `/api/admin/recommendation-priorities?criterion=...&schedule=...`로 지연 조회하는 방식을 우선 검토한다.

### 관리자 저장

`PATCH /api/admin/recommendation-priorities`

- 입력: `criterionTag`, `scheduleType`, 정렬된 `cruiseIds`, 마지막 조회 버전
- 검증: 관리자 권한, 중복 ID, 존재하는 크루즈, 태그 형식, 일정 코드
- 처리: 하나의 트랜잭션에서 전체 순위를 1부터 재배치
- 처리 후: `/travel-guide` 재검증
- 출력: 서버가 확정한 최종 순서, 저장자, 저장 시각, 새 버전

### 고객 추천

`/api/agent`의 `recommend` 모드에서 후보 계산과 함께 해당 범위의 순위를 서버에서 조회한다. 순위 조회가 실패하면 추천 전체를 실패시키지 않고 기존 점수 정렬로 안전하게 폴백하되 서버 경고 로그를 남긴다.

## 10. 구현 순서

### 1단계 — 데이터와 API

1. 홈페이지 전용 마이그레이션과 RLS 추가
2. 범위별 일괄 순위 저장 함수 구현
3. 관리자 조회·저장 API 및 관리자 역할 검증 구현
4. 기존 활성 태그를 기준으로 초기 순위는 모두 `미지정` 상태로 시작

### 2단계 — 관리자 화면

1. 추천 기준·일정 범위 선택 UI 구현
2. 순위 목록, 미지정 목록, 키보드 이동 구현
3. 변경 감지, 일괄 저장, 버전 충돌 처리 구현
4. 데스크톱 1440px과 모바일 390px 검증

### 3단계 — 추천 엔진

1. 고객의 첫 번째 선택을 1순위 추천 기준으로 명시
2. 범위 폴백 규칙 구현
3. 필수 적합성 이후 운영순위 정렬 적용
4. 운영순위가 없거나 조회 실패한 경우 기존 결과가 유지되는지 확인

### 4단계 — 검수와 배포

1. 운영순위를 결과에 적용하지 않고 로그만 남기는 shadow 검증
2. 대표 조건별 기존 순서와 새 순서 비교
3. 운영 담당자 승인 후 실제 정렬 활성화
4. 이상 시 기능 플래그를 끄면 기존 점수 정렬로 즉시 복귀하도록 구성

## 11. 필수 테스트

| 시나리오 | 기대 결과 |
| --- | --- |
| 같은 일정·인원·객실·예산, 같은 추천 기준에서 A=1위, B=2위 | A가 B보다 먼저 노출 |
| A=1위지만 객실 정원 부족 | A 제외, 다음 적합 순위가 상승 |
| A=1위지만 선택일의 활성 요금 없음 | A 제외 |
| 일정별 순위 없음, ALL 순위 있음 | ALL 순위 적용 |
| 태그별 순위 없음, default 순위 있음 | default 순위 적용 |
| 아무 순위도 없음 | 현재 점수·가격 정렬과 동일 |
| 추천 기준 두 개 선택 | 첫 선택의 운영순위, 두 기준의 점수 모두 반영 |
| 같은 크루즈 ID 중복 저장 | 400 오류, 기존 순서 유지 |
| 두 관리자가 같은 범위를 연속 저장 | 뒤 사용자는 충돌 안내, 자동 덮어쓰기 금지 |
| 순위 조회 장애 | 고객 추천은 기존 점수 방식으로 정상 반환 |
| 모바일 관리자 순위 이동 | 44px 버튼으로 이동·저장 가능, 가로 스크롤 없음 |
| 고객 결과 가격 표시 | 데스크톱·모바일 모두 오른쪽 정렬 유지 |

## 12. 완료 기준

- 관리자가 추천 기준과 일정을 선택해 여러 크루즈의 순서를 한 화면에서 변경할 수 있다.
- 저장 후 새로고침해도 동일한 순서가 유지된다.
- 같은 고객 조건을 다시 실행하면 적합 후보 안에서 저장한 운영순위가 재현된다.
- 부적합·비공개·요금 없음 상품은 운영순위와 관계없이 추천되지 않는다.
- 순위 미설정과 순위 서비스 장애 시 현재 추천 결과가 깨지지 않는다.
- 플랫폼 예약·견적·결제 계약과 기존 플랫폼 관리자 기능에는 변경이 없다.
- `/travel-guide` 결과 카드의 가격 오른쪽 정렬과 기존 상담·예약 안내 문구가 유지된다.

## 13. 권장 출시 범위

첫 출시는 `default`, `family`, `couple`, `value`, `luxury`와 `DAY`, `1N2D`, `2N3D` 범위만 운영하는 것이 좋다. 실제로 사용하지 않는 태그까지 한꺼번에 순위를 채우지 않고, 대표 고객 조건을 검수하면서 범위를 늘린다.

가장 중요한 운영 원칙은 **순위가 상품 적합성을 대신하지 않게 하는 것**이다. 관리자는 노출 우선권을 조정할 수 있지만, 일정·인원·객실·활성 요금 검증은 항상 먼저 실행되어야 한다.
