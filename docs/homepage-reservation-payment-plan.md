# 홈페이지 예약·결제 통합 계획

작성일: 2026-08-27
대상: `sht-homepage` → `sht-platform` 고객 예약·결제 흐름

## 결론

홈페이지는 상품 탐색과 선택을 담당하고, 회원·예약·견적·결제 원장은 예약
플랫폼 Supabase에만 둔다. 홈페이지 Supabase는 플랫폼 상품을 가공한 공개
캐시와 홈페이지 전용 콘텐츠만 유지한다.

```text
플랫폼 상품 원본 ──동기화──> 홈페이지 v2 공개 캐시 ──선택──┐
                                                          │
홈페이지 상품 상세 ──검증된 handoff────────────────────────┤
                                                          ▼
플랫폼 로그인 → 원본 요금 재조회 → 예약 → 견적 확정 → OnePay 결제 → 확정서
```

## 점검 결과

- 홈페이지와 예약 플랫폼은 서로 다른 Supabase 프로젝트다.
- 회원 인증은 홈페이지에서도 예약 플랫폼 프로젝트를 사용하고 있다.
- 플랫폼 상품 원본은 홈페이지 `*_v2` 공개 캐시로 동기화되고 있으며, 활성
  크루즈 25개·객실 219개·요금 854개가 확인됐다.
- 활성 요금 854개 모두 플랫폼 원본 `cruise_rate_card.id`를
  `rate_plans_v2.source_rate_id`로 보존하고 있어 두 DB를 안전하게 연결할 수
  있다.
- 기존 상품 상세의 예약 폼은 홈페이지 구형 `reservations`에 직접 INSERT한다.
  그러나 이 테이블은 빈 구형 `cruises/cabins`에 외래키가 걸려 있고 INSERT
  RLS 정책도 없어 현재 v2 상품으로는 정상 접수될 수 없다.
- 플랫폼 크루즈 직접 예약 화면은 현재 `quoteId`, `edit`만 읽는다. 홈페이지
  handoff 파라미터를 받아 초기값으로 쓰는 구현이 다음 단계에 필요하다.
- OnePay create/return/notify 코드는 플랫폼에 있으나 create 권한이
  manager/admin으로 제한되어 있다. 고객 셀프 결제는 별도의 권한·소유권 검증
  엔드포인트와 멱등 처리 후 열어야 한다.

## 목표 흐름

1. 고객이 홈페이지에서 크루즈·객실·일정·이용일·인원을 고른다.
2. 홈페이지는 개인정보 없이 플랫폼 원본 요금 ID와 선택 조건만 전달한다.
3. 플랫폼은 로그인 완료 후 원래 URL로 복귀한다.
4. 플랫폼이 `rateCardId`를 원본 DB에서 재조회하고 활성 상태, 적용 기간,
   객실명, 일정, 인원 규칙과 최종 금액을 다시 계산한다.
5. 고객 확인 후 플랫폼 `reservation`과 서비스별 상세 행을 하나의 트랜잭션
   또는 검증된 RPC로 생성한다.
6. 담당자 승인 또는 자동 확정 조건을 거쳐 `reservation_payment`를 만든다.
7. OnePay는 서버에서만 결제 URL을 만들고 서명된 IPN을 기준으로 결제 완료를
   멱등 반영한다. 브라우저 return은 결과 화면 표시용으로만 사용한다.
8. 결제 성공 후 예약·견적·확정서 상태를 한 트랜잭션으로 동기화한다.

## 구현 단계

### 0. 홈페이지 handoff 기반 — 구현 완료 / 운영 배포 대기

- [x] 구형 홈페이지 `reservations` INSERT 제거
- [x] 개인정보 없는 `/api/platform/booking-handoff` 추가
- [x] 플랫폼 원본 요금 ID를 공개 v2 조회 모델에 추가
- [x] 상품 상세 CTA를 플랫폼 예약 계속하기로 변경
- [ ] 운영 배포 후 실제 플랫폼 도착 URL 확인

### 1. 플랫폼 예약 prefill

- `source=homepage`일 때 전달값을 허용 목록으로 파싱한다.
- 로그인 리다이렉트 전 handoff URL 전체를 안전한 `next` 값으로 보존한다.
- `rateCardId`로 `cruise_rate_card`를 재조회하고 나머지 파라미터와 불일치하면
  원본 값을 우선한다.
- 홈페이지 객실 선택을 플랫폼의 `rate_card_id`/객실 선택에 연결한다.
- 아동·유아 생년월일과 객실 배치는 플랫폼에서 추가로 입력받는다.

완료 기준: 홈페이지 선택값이 로그인 후 플랫폼 폼에 재현되고, 수정 후 예약
행과 `reservation_cruise` 행이 생성된다.

### 2. 견적·고객 결제

- 고객 본인 예약만 결제할 수 있는 서버 API를 만든다.
- 결제 가능 상태, 미결제 잔액, 통화, 금액을 서버에서 재검증한다.
- OnePay 요청 참조값과 IPN 이벤트에 고유 제약을 두어 중복 처리를 막는다.
- 결제 상태 갱신, 견적 상태 갱신, 감사 로그를 DB 함수/트랜잭션으로 묶는다.
- 실패·취소·타임아웃·중복 IPN을 테스트한다.

완료 기준: 테스트 결제 1건이 중복 반영 없이 `completed`가 되고, 다른 사용자의
결제 ID로 요청하면 403이 반환된다.

### 3. 예약 후속 처리

- 결제 완료 화면, 예약 목록, 영수증과 확정서를 연결한다.
- 예약 변경·취소 및 환불 상태를 동일 원장에서 관리한다.
- 운영자 알림과 고객 알림은 결제 트랜잭션과 분리된 재시도 가능한 작업으로
  보낸다.

### 4. 확장

- 같은 handoff 계약을 호텔·투어·차량에 확장한다.
- 유입 채널 분석이 필요하면 플랫폼 `reservation`에 `origin_channel`과
  `origin_context jsonb`를 추가한다. 개인정보나 결제 원문은 넣지 않는다.

## DB 원칙

- 홈페이지 DB에는 예약·결제 원장을 새로 만들지 않는다.
- 홈페이지 공개 뷰에는 연결에 필요한 플랫폼 원본 ID만 노출한다.
- 플랫폼 INSERT/UPDATE는 인증 사용자 소유권을 확인하는 RLS 또는 서버
  API/RPC를 거친다.
- 가격은 브라우저·URL·홈페이지 캐시 값을 신뢰하지 않는다.
- 결제 완료는 서명 검증된 서버 알림을 기준으로 하고 멱등 키를 강제한다.
- service role/secret key는 서버 전용이며 `NEXT_PUBLIC_` 변수에 두지 않는다.

## 별도 보안 조치

홈페이지 프로젝트에서 아래 구형 9개 관계의 RLS가 꺼져 있다는 Advisor 경고가
확인됐다: `cruise_holiday_surcharge`, `cruise_info`, `cruise_info_view`,
`cruise_location`, `cruise_promotion_rate`, `cruise_promotion`,
`cruise_rate_card`, `cruise_rooms_view`, `cruise_tour_options`.

즉시 RLS만 켜면 기존 조회가 중단될 수 있으므로 이번 예약 변경에는 포함하지
않는다. 실제 사용처와 필요한 공개 컬럼을 확인한 뒤 읽기 전용 뷰 또는 명시적
SELECT 정책으로 전환하고, anon/authenticated의 쓰기 권한을 제거하는 별도
마이그레이션으로 처리한다.
