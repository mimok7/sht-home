# 결제 전 가격 선택 / 결제 후 운영정보 입력 계획

## 1. 목표

홈페이지 예약을 다음 두 단계로 분리한다.

1. 결제 전에는 상품 가격, 수량, 인원 구성, 가격표 선택에 필요한 일정만 입력한다.
2. 결제 완료 후에는 픽업·샌딩 장소와 시각, 항공편, 경유지, 요청사항 등 실제 운영에 필요한 정보를 입력한다.

고객이 결제 전에 긴 운영 양식을 작성하지 않도록 하되, 결제 금액은 기존 플랫폼 가격표를 다시 조회해 확정한다.

## 2. 변경하지 않는 경계

- 기존 `sht-platform` 애플리케이션과 플랫폼 Supabase 스키마, RLS, 함수, 트리거, 결제 API는 변경하지 않는다.
- 예약, 견적, 결제 원장은 계속 플랫폼 Supabase가 담당한다.
- 홈페이지 Supabase에는 기존과 같이 `homepage_booking_carts` 선택 초안만 저장한다.
- 결제 링크는 기존 매니저 발급 OnePay 흐름을 유지한다.
- 홈페이지의 결제 후 입력은 고객 소유 예약의 비어 있는 운영 컬럼만 최초 저장한다. 기존 값의 변경은 기존 플랫폼 변경요청/매니저 승인 절차를 사용한다.

## 3. 서비스별 입력 분리

| 서비스 | 결제 전 가격·상품 선택 | 결제 후 운영정보 |
| --- | --- | --- |
| 크루즈 | 출항일, 일정, 크루즈, 객실 타입·수, 연령별 인원, 엑스트라베드·싱글, 유료 옵션 | 커넥팅룸, 생일 이벤트 정보, 요청사항 |
| 크루즈 차량 | 연결할 크루즈, 단독/셔틀, 이용 방식, 경로, 차량 유형·수, 탑승·수하물 수 | 픽업·귀환 일시, 승하차 장소, 경유지·대기, 요청사항 |
| 공항 | 픽업/샌딩, 서비스 분류, 경로, 차량 유형, 요금 적용일, 탑승·수하물 수 | 공항명, 항공편, 정확한 일시, 숙소, 경유지·대기, 요청사항 |
| 호텔 | 체크인·체크아웃, 호텔·객실, 객실 수, 연령별 인원 | 요청사항 |
| 렌터카 | 이용 방식, 경로, 차량 유형·수, 탑승·수하물 수 | 픽업·귀환 일시, 승하차 장소, 경유지·대기, 요청사항 |
| 투어 | 투어, 이용일, 인원별 요금, 결제 방식, 유료 추가 옵션 | 픽업·하차 장소, 운영 요청사항 |

| 티켓 | 티켓·프로그램, 이용일, 인원·수량, 가격이 있는 셔틀·메뉴 옵션 | 셔틀 승하차 장소, 상세 운영 요청사항 |

`이용일`이 가격표 유효기간이나 객실 박수 계산에 쓰이는 서비스는 결제 전에 유지한다. 시각과 상세 장소는 결제 후로 이동한다.

## 4. 데이터 계약

### 장바구니

- 새 장바구니 항목은 `metadata.platform.contractVersion = 2`를 사용한다.
- 가격 재검증에 필요한 코드와 수량만 신뢰 가능한 입력으로 전달한다.
- 운영정보는 장바구니에 저장하지 않는다.
- 기존 버전 1 항목은 제출 API에서 계속 읽을 수 있게 유지하되, 새 폼에서는 만들지 않는다.

### 예약 생성

- 제출 시 플랫폼 가격표를 다시 조회하고 금액과 적용기간을 재검증한다.
- 예약 상세 행은 가격 코드·수량·인원·금액을 저장하고 운영 컬럼은 `NULL`로 둔다.
- `price_breakdown`에는 `operational_details_status: "pending"`을 기록해 새 흐름에서 생성된 예약임을 식별한다.
- 운영정보를 대신하는 가짜 장소·시각·항공편은 저장하지 않는다.

### 결제 후 운영정보

- 홈페이지 API에서 사용자 토큰, 예약 소유권, 결제 완료 상태를 다시 확인한다.
- `reservation.payment_status` 또는 연결된 `reservation_payment.payment_status`가 `completed`/`paid`인 경우만 입력을 허용한다.
- 허용 테이블과 컬럼은 서버 allowlist로 제한한다.
- 현재 값이 `NULL` 또는 빈 문자열인 컬럼만 저장한다. 이미 입력된 값은 덮어쓰지 않는다.
- 고객이 후속 변경을 원하면 기존 플랫폼의 변경요청·매니저 승인 흐름으로 안내한다.

## 5. 구현 순서

1. 서비스 폼에서 운영 입력과 결제 전 필수 검증을 제거하고 가격 조건 안내를 추가한다.
2. 장바구니 계약을 버전 2로 올리고 운영정보가 포함되지 않도록 정규화한다.
3. 예약 저장 API가 운영정보 없이 상세 행을 생성하도록 조정한다.
4. `/booking/reservations/[id]/operations` 화면과 API를 추가한다.
5. 내 예약 목록과 상세 화면에서 결제 완료 예약에 `운영정보 입력` 동작을 노출한다.
6. 미결제 접근, 타인 예약 접근, 기존 값 덮어쓰기, 잘못된 컬럼 전송을 차단하는 검증을 수행한다.

## 6. 완료 기준

- 모든 서비스에서 결제 전 화면에는 가격에 영향을 주는 선택만 표시된다.
- 장바구니와 체크아웃 금액이 기존 플랫폼 가격 재검증 결과와 일치한다.
- 장소·시각·항공편이 비어 있어도 예약 상세 행이 가짜 값 없이 생성된다.
- 미결제 고객은 운영정보 입력 화면에서 저장할 수 없다.
- 결제 완료 고객은 자기 예약의 빈 운영정보만 입력할 수 있다.
- 이미 입력된 운영정보는 홈페이지에서 수정할 수 없다.
- 데스크톱 1440px과 모바일 390px에서 금액은 오른쪽 정렬되고 가로 스크롤이 없다.
